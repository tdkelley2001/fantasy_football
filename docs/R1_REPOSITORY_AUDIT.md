## 1. Executive summary

The repository has a coherent engine/persistence/application boundary, locked dependencies, useful reference/oracle tests, privacy protections and a substantial operational evidence trail. The main collaboration problem is discoverability and drift: README is a long chronological catalog, several current references still introduce schema v3, setup information is spread across historical handoffs, and contributor workflow is largely implicit. No code/module/dependency was proven safe to delete.

The follow-up establishes the intended collaboration authority: `tdkelley2001/fantasy_football` remains the original, authoritative repository; both original-repository feature branches and the existing contributor fork are supported. Once implemented, reviewed pull requests are the route into `main`. GitHub Issues are proposed as the actionable-work authority, with GitHub Projects as the shared planning view. The existing fork needs no migration or deletion. These decisions and the proposed initial catalog below do not create GitHub resources or authorize feature implementation.

Highest-priority corrections are:

1. Reconcile the Node prerequisite with the **complete locked developer toolchain**, not just Vite. The installer accepts versions rejected by locked Vitest/jsdom engines.
2. Make one current installation/configuration/operation path explicit. Distinguish launcher `WAR_ROOM_DATABASE`/`--database` from Python `SNAPSHOT_DB_PATH`, and browser manual-rule configuration from CLI `--manual-config`.
3. Correct current schema and refresh instructions, while retaining dated audit claims as historical evidence. The browser defaults to automatic safe-boundary detection; an arbitrary next unstarted week cannot authorize skipping an unresolved current matchup.
4. Separate normative contracts, current how-to/reference material and archived evidence. Keep `MASTER_SPEC.md` authoritative throughout migration; do not silently rewrite accepted modeling requirements.
5. Establish contributor commands, review/branch policy, CI scope and compatible lint expectations. The narrow correctness gate passes, but a default Ruff sweep reports 252 findings and formatter checking would reformat 99 Python files. Neither is a license for an automatic repository-wide rewrite.

Lightweight checks passed: **68 documentation/security tests**, both frontend TypeScript configurations with emission/incremental writes disabled, Python dependency consistency, installed frontend dependency-tree consistency and the repository's narrow Ruff correctness rules. A broader scan found **no missing targets among 105 tracked local Markdown/image links**. This does not validate fragment anchors, bare code-path references, rendering or external URLs. No fresh installation, browser workflow, full regression suite, npm network audit, ESPN operation, database operation or process recovery was executed in R1.

## 10. Two-contributor collaboration and backlog policy

### Repository authority and contribution routes

`tdkelley2001/fantasy_football` is authoritative for accepted code, documentation, issues and pull requests. The existing fork stays in place. A contributor may work on a feature branch in the original repository where permissions allow, or on a feature branch in their fork. Both routes submit a PR whose **base repository is `tdkelley2001/fantasy_football` and base branch is `main`**. Issues belong in the original repository even when implementation happens in a fork; avoid maintaining a second issue backlog or planning board in the fork.

Once R2 establishes the workflow, all changes to upstream `main`, including documentation and coding-agent changes, enter through reviewed PRs. Propose one review by the other contributor or an agreed independent reviewer, relevant verification and resolved review comments before merge. Configure available branch/ruleset protections only after confirming contributor/reviewer permissions and required checks. No self-approval substitute, routine direct push to upstream `main`, history rewrite, fork deletion or repository migration is part of this plan. Existing accepted commit history is not rewritten to retrofit the new workflow.

Use small issue-linked branches, for example `docs/issue-id-short-topic`, `fix/issue-id-short-topic`, `feature/issue-id-short-topic` or `research/issue-id-short-topic` (replace the illustrative issue identifier). The assignee, if any, owns coordination rather than exclusive ownership of a module. Before overlapping changes, note the files/interfaces being touched and agree sequencing in the upstream issue. Branches and PRs should remain independently reviewable and preserve the standing spec/evidence/compatibility rules.

### Syncing a fork or original-repository branch

These are **future contributor instructions, not commands executed in R1**. Check `git status --short` first and deliberately preserve any local work. Inspect `git remote -v`; add the upstream remote only if absent, and verify an existing one rather than silently replacing it. Substitute the contributor's actual branch name below.

For a fork checkout, `origin` points to the retained fork and `upstream` to the original repository:

```shell
git remote add upstream https://github.com/tdkelley2001/fantasy_football.git
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main
git switch -c feature/issue-id-short-topic
```

The `git push origin main` in this example synchronizes **the fork's** main only; it is not permission to push upstream main. If a fast-forward fails, stop and inspect divergence; do not reset, discard commits or force-push. “Already up to date” also does not prove that local main has no extra commits: inspect ahead/behind state before using it as a branch base. Preserve existing work and coordinate any divergence; review the complete PR diff against authoritative main so unrelated fork commits are not included accidentally. Make the contribution on its feature branch and open the PR against upstream main, not against the fork's main.

For a checkout of the original repository, `origin` is authoritative:

```shell
git fetch origin
git switch main
git merge --ff-only origin/main
git switch -c feature/issue-id-short-topic
```

To update an existing feature branch, fetch the authoritative remote, switch to the actual feature branch, merge `upstream/main` (fork route) or `origin/main` (original-repository route), resolve any conflicts with the affected contributor, rerun relevant checks and push the feature branch with `git push -u origin your-feature-branch`. Default to merging when sharing a branch; do not rewrite another contributor's published commits. A private-branch rebase can be agreed separately, but it is unnecessary for this workflow. Bring late upstream changes into the PR before final verification/review when they affect its interfaces.

| Blocking flag | `blocked` | Independent of status. Record the dependency issue, missing evidence/approval/access, next unblocking action and responsible contact in the issue body/comment. Never hide a blocked item by marking it Done. |
| Ownership | Optional assignee to either contributor | Assignment is optional and agreed; use a named reviewer in the PR. Confirm actual assignment/Project permissions during R2, without migrating or removing the fork. |

Backlog means a recorded, triaged proposal. Ready requires a bounded objective, governing context, acceptance/verification criteria, satisfied implementation approvals and actionable dependencies. In Progress means a contributor is actively doing that work. In Review means a linked PR or research/design artifact awaits review. Done requires acceptance criteria and recorded verification plus reviewed/merged upstream changes where applicable, or an accepted research/design conclusion. Then close the issue. An accepted finding of “unsupported” can finish a research issue without marking the proposed product feature implemented. Work blocked during implementation retains its truthful status and gains the independent flag; research awaiting external evidence normally stays in Backlog with that flag. Rejected/duplicate proposals may be closed with an explicit reason, rather than counted as delivered functionality.

For two contributors, one small board is sufficient: columns by status, a priority-sorted backlog view, and a blocked-work view. Do not add compulsory estimates, sprints, story points or duplicated milestone fields. Agree the next one or two Ready issues during brief regular triage; link PRs and blockers as work progresses. Review assignments and priority changes together when they affect a shared interface or milestone gate. Keep accepted modeling rules in the specification, not in mutable labels or board automation.

### Lightweight issue and PR templates

Propose three issue templates covering the five types: **Bug**, **Work proposal** (enhancement/documentation/technical debt) and **Research**. Keep the shared fields short: objective/problem, relevant source/spec/context, acceptance criteria and verification plan; optional dependency/blocker, assignee and out-of-scope notes. Bugs additionally capture expected/actual behavior, a sanitized reproduction and affected version. Research additionally states the question, evidence needed, authorized collection boundary and what would count as verified, unavailable or inconclusive. Never request credentials, raw private ESPN responses, private databases or user results as routine attachments.

The PR template should contain: linked upstream issue and governing contract; concise problem/change; acceptance criteria addressed; exact checks/results plus skipped checks and reasons; and any compatibility/evidence/behavioral impact. Use screenshots only for relevant visual changes and keep them sanitized. Link remaining blockers instead of burying them in prose. Use GitHub closing references only for the actual accepted scope; a preparatory PR should not close a larger feature issue prematurely. A PR from the fork still links the issue in the original repository, using a fully qualified issue reference where needed.
