## Recommendation and constraints

Pilot the proposed nine-document arrangement as a **reader architecture**, subject to the owner boundaries and consumer gates below. It is more intuitive to start with the quantitative experiment, data and assumptions, then evaluate its correctness/validity and use its results. The proposed arithmetic is **five existing paths retained + four new paths = nine**, requiring retirement of twelve current paths only after their section transfers are accepted (a net reduction of eight). That migration is not yet safe: M0 has executable evidence-role bindings, current tests assert the 17-owner set, and large combined methodology/technical documents need a navigation pilot. Nine is a hypothesis to evaluate, not a deletion quota.

The current collection is not merely module documentation: it already carries precise domain contracts. Its weaknesses are mixed reader purposes within sections (equations beside hashing bytes, user tasks beside frontend race contracts), scattered assurance standards and repeated limitations/status pointers. Reorganize by **meaning → evidence → use → implementation**, while retaining every exact algorithm, unsupported input case, evidence condition and accepted successor. The 202 rows below map every H1/H2/H3 heading, including body-less containers and introductory/navigation content, not just 17 file-level destinations.

A first-reading path should be README → METHODOLOGY M1 → DATA D1–D5 → METHODOLOGY M2–M9 → VALIDATION V0–V4. An operator can instead go straight to USER_GUIDE; a maintainer uses TECHNICAL_REFERENCE and CONTRIBUTING without learning a second set of mathematical definitions. Pending requirements stay visible through BACKLOG. Current provisional methods never become scientifically validated through this architecture change.

## Proposed responsibility and boundary model

| Reader question | Sole substantive owner | Boundary / rule |
|---|---|---|
| What is War Room and what can I currently use? | README | Short capability/release matrix; no second backlog, formula catalog or operating manual. |
| What is observed, transformed, missing, trusted or unsupported? | DATA | Endpoint/field authority, transformations, data assumptions/quality, temporal and manual source evidence. Record layouts/serialization link T2; numerical treatment links M2/M4. |
| What experiment and decision model are being calculated? | METHODOLOGY | Path/season/transaction algorithms, outcome assumptions, estimators/inference, action comparison and decision limits. Preserve full equations/pseudocode and edge cases, not a high-level replacement summary. |
| Why should I trust this implementation, arithmetic, data or decision? | VALIDATION | Four separate assurance questions; actual evidence versus required/future validation and component-specific promotion. It does not choose algorithms or own a test-run diary. |
| How do I install, operate and interpret it? | USER_GUIDE | Current task sequence and safe operation. Developer setup/check commands remain CONTRIBUTING; public shape is T5, formulas M7. |
| How is the approved model represented/executed/integrated? | TECHNICAL_REFERENCE | Typed contracts, exact identities/versions/serialization, APIs, workers/checkpoints, indexing/storage, process/frontend integration and security. Links authoritative algorithms instead of reproducing them. |
| What remains to be done and what approval is needed? | BACKLOG | All stable open requirements, defects/research/proposals, acceptance/dependencies and status. A methodological or scientific requirement may be approved while its proposed implementation is unselected. |
| What controls apply to changes? | AGENTS / CONTRIBUTING | Standing engineering/evidence/approval controls versus contributor/check/review procedures. Independent reviewer may be the other contributor or agreed reviewer; no invented organizational separation or external compliance claim. |

### Methodology versus implementation decision rule

Place a statement in METHODOLOGY if changing it could change the mathematical experiment, legal action universe, lineup/scoring result, estimand, coverage promise, uncertainty or ranking meaning. Place exact Python/HTTP fields, byte encodings, schema versions, file/database layouts, resource/executor/replay protocols and runtime error envelopes in TECHNICAL_REFERENCE. A precise analytical edge case remains in M even when code currently violates it; T documents the implemented interface/limitation, V the missing proof and B the remediation gate. Neither side silently overrides the other.

Examples: M2b owns the Normal equation; T3 owns its historical private three-parameter draw key versus corrected public missing-projection policy discriminator and old-checkpoint rejection. M6 explains a matched path and N-denominator; T3/T6 own exact seed/hash/range/worker/checkpoint binding. M4 owns once-only fixed/remaining/carry composition and use restrictions; D5 owns independent source/lock/cutoff authority; T4 owns companion artifact 1 and serialization. M7 owns fraction/point mathematics, T5 the accepted legacy API pass-through and U5 current display interpretation. No new scaling is implied. M8 owns finite action/complete-state equivalence; T7 owns index/page/schema and bounded queues. C13 lifecycle ownership is T8, not another probability method.

## Validation evidence and promotion

Keep four different questions visible. Their answers are not interchangeable:

| Assurance question | Evidence currently available to preserve | Unfulfilled proof / promotion gate |
|---|---|---|
| Implementation correctness: does code implement specified rules? | Hand-checkable deterministic league fixtures; independent exhaustive lineup/allocation/cycle/sequential references with distinct objectives; canonical/eligibility/partial negative cases; API/UI/request-state tests. | WR-023 extreme finite arithmetic, WR-024 incomplete V(R) selection, WR-026 later index-failure cleanup and unsupported rule/live permissions remain explicit. Source-inspected discrepancies are not fixed by prose. |
| Numerical correctness: are paths, estimators, identities and intervals calculated correctly? | Historical Normal reference/goldens; missing-versus-zero/signed generation tests; paired/absolute interval references; path/seed/worker/batch/resume equality; all-unstarted partial equivalence and retained benchmark artifacts. | WR-025's repeated-look paired stopping/display family remains unproven; separate candidate-ranking allocation does not certify it. Preserve no-renormalization and complete-prefix checks. No statistical-method change is approved. |
| Empirical validity: are outcomes supported by genuine temporally valid data? | Source/dataset/capture validation and exploratory scoring/report machinery are test-supported; bounded live field observations retain their exact scopes. | Authentic pregame projections/actuals, training/validation/sealed-test/tuning isolation, representative position/projection/zero/signed/tail calibration, sparse sensitivity and prospective evidence remain WR-019. Current one-boundary evaluation and exploratory CRPS are insufficient. |
| Decision validity: are recommendations useful/reliable under assumptions? | Matched scenario/state comparisons, legal finite enumeration, disclosed screens/caps and deterministic proxy reference behavior. | WR-008 requires sampled proxy ordering/selected actions/replacement outcomes versus higher-fidelity full simulation, sensitivity/error/cost and realistic workloads. Finalist/selection uncertainty and model sensitivity remain separate from exact enumeration. No manager acceptance/waiver-success model is inferred. |

V0 should have a compact, component-scoped evidence map: claim, governing method/version, input/snapshot/data identity, evidence class, actual source/test/artifact, limitation, unresolved item and independent acceptance reference. Keep only decision-relevant evidence; commands/results for ordinary delivery stay Git/PRs, check procedures C2/C3. This is not a new evidence database or automatically generated model registry.

Promotion requires explicit component-specific criteria, a reproducible incumbent comparison and independent acceptance. Outcome distribution, proxy valuation, waiver mechanics, pruning and numerical optimization have different jobs; no universal score/minimum sample threshold promotes all of them. Validate calibration/support and decision consequences where relevant, reference equality for exact optimization, runtime/memory regressions and temporal/source trust. Retain original versus retrospective forecasts and raw versus sampled/calibrated means. New versioned models, bias correction, correlations or conditional in-game distributions require their own approval; this plan installs none. Current model_id/ordered parameters are authoritative T3 metadata; README links availability, not a second manually maintained version ledger.
